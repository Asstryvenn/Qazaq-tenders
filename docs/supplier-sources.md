# Каталог поставщика: подключение и синхронизация

## Три способа подключения

| Способ | Где обрабатывается | Требования сервера |
| --- | --- | --- |
| Excel (.xlsx) / CSV | Файл читается в браузере, на сервер уходят нормализованные товары пакетами по 500 | Миграции 0008 + 0009 |
| XML по ссылке (YML, Kaspi-подобный) | Сервер, `/api/supplier/sources` + синхронизация | + `SUPABASE_SECRET_KEY`, `SUPPLIER_SOURCES_ENC_KEY` |
| 1С OData / REST | Сервер, тот же конвейер | то же |

Лимиты — `lib/supplier-catalog/limits.ts` (файл 15 МБ, 20 000 строк, 20 000 товаров на поставщика,
фид 20 МБ, 1С до 30 000 элементов на сущность). Лимит каталога продублирован в SQL (`_supplier_upsert_products`).
Тело одного запроса к API не превышает ~3,5 МБ: лимит Vercel на тело функции — 4,5 МБ.

`.xls` (Excel 97–2003) **не поддерживается**: файл распознаётся по сигнатуре и пользователь получает
просьбу пересохранить его в .xlsx или CSV. Макросы, внешние связи и OLE не извлекаются, формулы не
вычисляются — используется сохранённое Excel значение.

Библиотеки: `fflate` (MIT, без зависимостей) — распаковка ZIP с проверкой объявленных размеров;
`fast-xml-parser` (MIT) — XML. SheetJS из npm (0.18.5) не выбран из‑за неисправленных CVE, ExcelJS —
из‑за размера и отсутствия лимитов распаковки.

## Конвейер

`fetch → parse → normalize → validate → diff → commit` (`lib/supplier-catalog/sync-core.ts`).

* Ошибка загрузки, обрезанный/битый XML, 401/403, неполная пагинация → ничего не записывается.
* Товары, пропавшие из источника, скрываются (`active=false`, `deactivated_reason='missing_from_snapshot'`)
  только в режиме «полный снимок», после полной успешной обработки и если снимок не меньше 50 %
  активных товаров (при ≥ 20 товаров). Пустой снимок не скрывает ничего.
* Строки, которые есть в источнике, но не прошли проверку, тоже не скрываются.
* Повторный запуск идемпотентен: upsert по коду товара, хеш содержимого → «без изменений».
* Один запуск на источник одновременно (`claim_supplier_source`, блокировка 120 с); прерванные запуски
  закрываются как `interrupted`.
* Временные ошибки (5xx, сеть, тайм-аут, 429) — 3 попытки с экспоненциальной задержкой; `Retry-After`
  до 15 с выдерживается, больше — запуск переносится на это время.
* 401/403 → источник ставится на паузу (`paused_reason`), автозапуски прекращаются до переподключения.
* «Обновить сейчас» — не чаще раза в 2 минуты (атомарная отметка в БД).
* Журнал — `supplier_sync_runs`; в нём и в логах только код ошибки и очищенный текст (`redactSecrets`).

## Безопасность

* Секрет источника (полный URL с токеном, логин/пароль 1С) — AES-256-GCM, ключ `SUPPLIER_SOURCES_ENC_KEY`,
  ID источника как AAD. Таблица `supplier_source_secrets` недоступна `anon`/`authenticated`. API возвращает
  только `display_url` без параметров.
* SSRF (`lib/server/safe-fetch.ts`): только https, без логина в URL, порт 443 или ≥ 1024; запрет
  localhost/*.local/*.internal/однословных имён и metadata-хостов; все адреса DNS-ответа должны быть
  публичными (IPv4 и IPv6, включая IPv4-mapped, 6to4, NAT64); соединение открывается на проверенный
  адрес (защита от DNS rebinding); редиректы с учётными данными запрещены, без них — до 3, каждый
  проверяется заново, `Authorization`/`Cookie` на другой origin не передаются; лимит скачанных и
  распакованных байт, общий тайм-аут, проверка TLS-сертификата не отключается.
* XML с `DOCTYPE`/`ENTITY` отклоняется целиком (XXE, «billion laughs»).
* Учётные данные 1С не передаются в LLM; ИИ в синхронизации не используется.

## Расписание

`vercel.json` вызывает `/api/cron/supplier-sync` раз в сутки (работает на любом тарифе Vercel; на Hobby
более частые cron-задачи не разрешены). Для обновления каждые 5–15 минут нужен внешний планировщик:

```bash
curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://<домен>/api/cron/supplier-sync
```

Варианты: GitHub Actions (`schedule: */10 * * * *`), cron-job.org, Supabase `pg_cron` + `pg_net`.
После настройки задайте `SUPPLIER_SYNC_SCHEDULER_INTERVAL_MINUTES` — интерфейс покажет реальную частоту.
Каждый вызов обрабатывает до 10 «созревших» источников в пределах ~45 с. Браузер ничего не планирует.

## XML по ссылке

* **YML**: `yml_catalog/shop/offers/offer`. Ключ — `offer@id` или `vendorCode`. `available="false"` = «под заказ».
  Остаток — `count`, склады — `outlets/outlet@instock`. Валюта — `currencyId` (публикуются только KZT).
* **Kaspi-подобный**: `kaspi_catalog/offers/offer@sku`, `model` (название), `brand`,
  `availabilities/availability@storeId,@stockCount,@available,@preOrder`, `cityprices/cityprice@cityId` или `price`.
  Это чтение файла поставщика, не интеграция с внутренним каталогом маркетплейса.
* Несколько складов: остатки хранятся по складам (`locations`), без выбора склада количество не суммируется.
  Разные цены по городам хранятся в `regional_prices`; если они различаются, нужно выбрать город.
* НДС форматом не определяется — его указывает поставщик.
* Дата данных — атрибут `date` фида, иначе `Last-Modified`; если обе неизвестны, цена не применяется к расчёту.

## 1С OData

Специалист 1С публикует стандартный интерфейс OData базы по HTTPS и создаёт отдельного пользователя
только для чтения (номенклатура, цены, остатки). Пароль администратора, ЭЦП и банковские доступы не нужны.

1. «Проверить соединение» читает `$metadata` (≤ 8 МБ, без DTD) и предлагает сопоставление по типовым
   именам (`Catalog_Номенклатура`, `InformationRegister_ЦеныНоменклатуры/SliceLast()`,
   `AccumulationRegister_ТоварыНаСкладах/Balance()`). Это только предложение: состав зависит от конфигурации.
2. Пользователь выбирает сущности, ключ связи (`Ref_Key`), поля, фильтр вида цен (`$filter`), поле склада.
3. Предпросмотр читает все страницы (`$top`/`$skip` или `odata.nextLink` внутри сервиса).
4. После подтверждения источник сохраняется и сразу синхронизируется.

Группы (`IsFolder`) и помеченные на удаление элементы пропускаются. Несколько цен у товара → ошибка строки
(уточните фильтр вида цен). Строки остатков одного склада складываются, разных складов — нет.

## REST-контракт Qazaq Tenders

`GET {url}?page=1&page_size=500` с `Authorization: Basic …` или `Bearer …`:

```json
{
  "items": [
    {
      "id": "A-1",
      "name": "Ноутбук Lenovo V15",
      "price": 289990,
      "currency": "KZT",
      "vat_included": true,
      "availability": "in_stock",
      "stock": 7,
      "locations": [{ "id": "ALM", "name": "Склад Алматы", "city": "Алматы", "stock": 3, "availability": "in_stock" }],
      "brand": "Lenovo", "model": "V15", "unit": "шт", "category": "Ноутбуки",
      "description": "…", "url": "https://shop.kz/p/a-1",
      "attributes": { "ОЗУ, ГБ": "16" },
      "updated_at": "2026-10-02T08:00:00Z"
    }
  ],
  "next_page": 2,
  "generated_at": "2026-10-02T08:00:00Z"
}
```

`id`, `name`, `price`, `currency` обязательны; `next_page: null` — последняя страница (страницы идут подряд).
`vat_included`, `stock`, `availability` могут быть `null`/отсутствовать — тогда значение «неизвестно».

## JSON для разработчиков

`POST /api/supplier/catalog` `{ "action": "preview" | "import", "runId": null, "products": [...] }` с
`Authorization: Bearer <access token>`, до 500 товаров в пакете, затем
`{ "action": "finish", "runId", "invalid": 0, "failed": false }`. Формат товара — `NormalizedProduct`
(`lib/supplier-catalog/types.ts`), пример — `public/samples/supplier-test.json`.

## Подбор под тендер

`SupplierPanel` показывает: поставщика, товар, цену (или цену для города лота), склады и известный остаток,
НДС (включён / не включён / неизвестно), дату данных источника и время синхронизации, уровень:
«найден кандидат» / «характеристики совпадают частично» / «нужна проверка» / «поставщик подтвердил
предложение» (через заявку). Совпадение слов не считается соответствием ТЗ. «Применить к расчёту»
доступно только для лота из одной позиции, с совпадающей единицей, данными источника не старше суток,
достаточным заявленным остатком и подтверждённым НДС, и после подтверждения человеком. Импорт не меняет
статус достоверности экономики (`verifiedFields`).

## Заявки

Покупатель отправляет заявку с явным согласием передать контакты (`create_supplier_inquiry`, ≤ 30 в сутки).
Поставщик подтверждает цену/количество/НДС/срок или отказывается (`respond_supplier_inquiry`).
Комиссий и выручки на этом этапе нет.

## Что проверено и что нет

Проверено автотестами: парсеры на fixtures (в т. ч. XLSX из openpyxl), адаптеры 1С на подставном HTTP,
SSRF и лимиты транспорта на локальном TLS-сервере, SQL/RLS на PGlite с эмуляцией ролей Supabase.
**Не проверено**: реальные экземпляры 1С и реальные фиды поставщиков, миграции на облачной Supabase,
внешний планировщик.
